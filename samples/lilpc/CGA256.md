# CGA-256: a hypothetical 160x100x256 packed-pixel extension

This documents a fictional CGA extension emulated by lilpc. It adds a
packed-pixel mode of 160x100 at 256 colors, with a RAMDAC color
look-up table, while keeping the whole frame inside CGA's existing
16KB of video memory.

## Why 160x100

The mode is constrained by two numbers: one byte per pixel and 16KB of
VRAM. 160 times 100 is 16000 bytes, which fits in 16384 with 384 bytes
to spare. The next step up, 320x200, needs 64000 bytes and does not
fit, which is exactly why standard CGA packs its graphics modes down to
2 or 1 bits per pixel. 160x100 is the largest one-byte-per-pixel frame
that fits the budget, and its aspect ratio is close enough to 4:3 after
display scaling.

## Hardware components and emulation decisions

The design brief listed four hardware additions. Here is how each maps
to the emulator, with pushback where the emulation differs from the
hardware reasoning.

### 1. 8-bit pixel sequencer

The hardware would bypass the 1bpp/2bpp shift register and pass a whole
byte per pixel clock straight to color mapping. In the emulator this is
just a render routine that reads one byte per pixel. No bit unpacking.

Mode select uses bit 6 (0x40) of the mode-control register at port
3D8h. Real CGA leaves bits 6 and 7 undefined, so this is a safe place
to put a new enable bit without colliding with existing software or
the 160x100 text trick. The renderer checks this bit ahead of the
normal text/graphics selection, matching the idea that the new
sequencer bypasses the old path.

### 2. RAMDAC color look-up table

Standard CGA is digital RGBI with a fixed 16-color pool, so 256 colors
require a RAMDAC with a 256-entry CLUT. The emulator implements a
256-entry table of 6-bit R,G,B components, programmed through ports
3C6h to 3C9h.

Pushback on period accuracy: a 6-bit, 262144-color DAC is an MCGA and
VGA concept from 1987, later than CGA. The brief explicitly cited the
MCGA/VGA 18-bit palette as the model, so the design follows it. Reusing
the real VGA port numbers (3C8h write index, 3C9h data) is a deliberate
bonus: palette-loading code written for VGA works here unchanged.

On the display side the CLUT is a 256x1 RGBA texture sampled by the CRT
shader. This replaces the previous 16-entry uniform array. A 256-entry
vec4 uniform array would exceed the guaranteed GLES3 fragment uniform
limit, so the look-up texture is both the faithful RAMDAC model and the
portable choice. All modes now run through this one palette path.

### 3. Linear video addressing

Standard CGA graphics interleave even and odd scanlines into two 8KB
banks. The packed mode uses linear addressing instead: pixel (x,y) is
at byte y*160 + x, with no bank swap. This is trivial in emulation and
matches the brief.

The CRTC start address (in word units, as in the other modes) is still
honored, so a program can pan or page-flip within VRAM. One real
limitation: a full second page needs 32000 bytes and only 16384 are
available, so double buffering does not fit. Start-address tricks are
limited to partial scroll.

On real hardware the linear layout is not a separate feature. It is the
same gate that produces line duplication, worked out in the scan-out
model section below.

### 4. MC6845 clock and scanline doubling

This is where the emulation intentionally diverges from the hardware
reasoning. On real silicon the CRTC would need a scanline doubler and a
pixel-clock divider so 100 lines sweep across 200 physical scanlines
and 160 pixels stretch to fill the width.

In the emulator none of that is needed for correctness. The renderer
produces a 160x100 index buffer and the existing display path upscales
it to the window with the same CRT shader, scanlines and aspect
handling used by every other mode. The status register timing stays at
the standard 262-line cadence, so software that polls vertical retrace
still works. The CRTC is not reprogrammed for pixel fetch in this mode.

The next section works out how the real hardware would actually put 100
lines of data onto the screen, since the answer turns out to explain
the linear addressing of point 3 as well.

## Scan-out model: how 100 lines reach the screen

A CGA monitor is a fixed 15.75 kHz horizontal, roughly 60 Hz vertical
NTSC-timed display: about 262 total scanlines per frame, about 200
active. The beam cannot scan fewer lines without the monitor losing
sync. So a 100-line mode never means the beam sweeps 100 times. It means
the 200 active scanlines are filled with 100 logical lines, each shown
twice. The real question is which piece of logic produces the repeat.

### CGA already runs graphics as 100 rows of 2 scanlines

The MC6845 does not think in scanlines, it thinks in character rows,
each R9+1 scanlines tall. For every scanline inside a character row it
emits two things:

- MA, the memory address, which increments once per character and stays
  the same across all subscanlines of the row.
- RA, the raster address, 0 to R9, which subscanline you are on.

Standard CGA graphics is already programmed as 100 character rows of
height 2 (R6 = 100, R9 = 1). It produces 200 unique lines only because
the card's glue logic feeds the low raster bit RA0 into the VRAM address
as the bank-select bit (A13, the 0x2000 offset). That is the even/odd
interleave:

    standard:  addr = (RA0 << 13) | MA     ; RA0 picks bank 0 vs bank 1

The top subscanline (RA0 = 0) reads MA, the bottom (RA0 = 1) reads
MA + 0x2000, two different bytes, so 200 unique lines.

### The packed mode gates RA0 out of the address

Line duplication needs no new CRTC feature. Keep R6 = 100 and R9 = 1,
and put one gate on the RA0 path, controlled by the mode bit:

    A13 = RA0 AND (NOT packed_mode)

- packed_mode = 0: A13 = RA0. Interleaved, 200 unique lines, normal CGA.
- packed_mode = 1: A13 = 0. RA0 no longer reaches the address, so both
  subscanlines of a character cell resolve to the same byte and the row
  is duplicated.

This is a static per-mode gate set by the mode register, not something
toggling per scanline, and the 6845 itself is unaware of it. The repeat
lives in the card's address logic, not in the CRTC.

### Linear addressing and duplication are the same gate

Forcing A13 to 0 does double duty, which is why it is the whole trick:

1. It collapses the two 8KB banks into one contiguous region. That is
   the linear addressing of point 3.
2. It makes both subscanlines fetch the same byte. That is the
   duplication.

They are not two features, they are one gate. To make the duplicated
lines also form a clean 160-byte-per-line packed framebuffer, the only
extra step is programming R1 (horizontal displayed) to 160 so MA
advances by 160 per character row and counts MA = row*160 + col on its
own. The fetched byte then goes straight to the RAMDAC with no shift
register.

### Contrast with VGA and MCGA

VGA and MCGA run a 31.5 kHz, roughly 400-line display, so they do the
opposite. They do not gate an address line, they repeat the raster
counter inside the integrated CRTC: the Maximum Scan Line register
(index 0x09) has a scan-doubling bit that holds the row-start address
for two physical lines. MCGA relies on this, as you recalled: its text
is an 8x16 cell over 400 lines, and 320x200x256 is double-scanned 200 to
400. A 100-line mode on that hardware would have to quad-scan to fill
400 lines. Same visible result, opposite mechanism: CGA ignores a raster
address bit, VGA repeats the raster counter.

In this emulator neither mechanism is modeled directly. The renderer
emits the 160x100 buffer and the display shader upscales it, which is
the duplication done at the output stage instead of the address stage.
The visible result is identical.

## Register map

| Port  | Access | Function                                             |
|-------|--------|------------------------------------------------------|
| 3D8h  | W      | Mode control. Bit 3 (0x08) display enable, bit 6 (0x40) packed-256 enable |
| 3C6h  | R/W    | PEL mask register                                    |
| 3C7h  | W      | PEL read index (then read triplets from 3C9h)        |
| 3C8h  | W      | PEL write index (then write triplets to 3C9h)        |
| 3C9h  | R/W    | PEL data: R, G, B in sequence, 6 bits each, auto-increments the index after B |

To enable the mode a program writes 0x48 to 3D8h (display enable plus
packed-256). The border color still comes from the low nibble of the
color-select register at 3D9h, indexing CLUT entries 0 to 15.

## Memory layout

- Base: B8000h, same as standard CGA.
- Size: 16000 bytes used of the 16KB window.
- Format: one byte per pixel, each byte a CLUT index 0 to 255.
- Addressing: linear, offset = y*160 + x.

## Default palette

At reset the CLUT is seeded so an unprogrammed palette is not pure
black. Indices 0 to 15 mirror the fixed CGA RGBI colors down-converted
to 6 bits, and 16 to 255 form a grayscale ramp. Most programs will load
their own palette through the RAMDAC ports.

## Demo

`cga256pack.c` is a host tool that converts a PNG to a packed-mode blob:
a 768-byte RAMDAC palette (256 entries, 6-bit R,G,B) followed by 16000
pixel indices. It area-resamples the image to 160x100, reduces it to
256 colors with a median-cut quantizer, and maps pixels with
Floyd-Steinberg dithering (`--nodither` to disable).

`viewer256.asm` is a .COM stub that loads the blob: it programs the
RAMDAC through 3C8h/3C9h, writes 0x48 to the mode register, and copies
the pixels to B800:0000.

`build-cga.sh` builds `cabin256.com` and `lake256.com` from the
full-color `cabin.png` and `lake.png`, then copies them onto
`disk/demodisk.img`. Run either from the DOS prompt and press a key to
return to text mode.

## Emulation boundaries

This is a rendering and I/O model, not a cycle-accurate chip. It does
not model CLUT read latency, DAC settling, or snow in the packed mode
(the packed renderer ignores the snow bitmap, since the mode implies a
dual-ported or faster memory path than the original CGA).
